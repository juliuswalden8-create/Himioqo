## Existing architecture

**Stack.** Next.js 15 App Router, React 19, TypeScript, Tailwind v4, shadcn/ui,
Radix, Lucide, Zod, `date-fns`, `qrcode`, Recharts. Supabase and Resend are
installed and there is a `supabase/schema.sql`, but neither is required to run.

**Data layer.** `src/lib/data/store.ts` is a single in-memory store held on
`globalThis.__hqStore5`, seeded from `src/lib/data/seed.ts` and
`src/lib/data/guide-seed.ts`. Every read helper takes an `organizationId` and
filters on it, so tenant isolation is already the default shape. Mutations go
through server actions in `src/lib/actions.ts`, `cleaning-actions.ts`,
`guide-actions.ts`, `guide-actions.ts` and `signup-actions.ts`.

**Auth.** Cookie `homioqo.session` holding `profileId:organizationId`, validated
in `src/lib/session.ts`. `src/middleware.ts` guards `/app/:path*` on cookie
presence only; the layout re-validates the session properly.

**Public token routes.** `/g/[token]` guest guide, `/qr/[token]` printable sign,
`/c/[token]` cleaner portal, `/t/[token]` guest report confirmation, `/r/[token]`
redirect. Tokens are 18 random bytes hex with a prefix, generated by
`createToken()`.

**i18n.** `sv` and `en` are full hand-written dictionaries in
`src/i18n/messages.ts`; `es` is a partial overlay. Every other locale is
translated from `en` at runtime through DeepL when `DEEPL_API_KEY` is set, and
falls back to the untranslated English string otherwise. Locale lives in the
`homioqo.locale` cookie.

**Design tokens.** `src/app/globals.css` `@theme` defines the navy/green/canvas
palette plus six `status-*` colours. `src/lib/status.ts` maps enum values to
Tailwind classes, so status colour is already centralised.

## Gaps found

Ordered by the priority list in the brief.

1. **Status labels are hardcoded Swedish** in `src/lib/labels.ts`. `StatusBadge`
   renders Swedish regardless of the selected locale. This breaks the project's
   own i18n rule and leaks into the manager dashboard everywhere.
2. **The manager cannot act on an issue.** `changeStatusAction`,
   `assignContractorAction`, `markResolvedAction` and `addAfterPhotosAction` all
   exist in `src/lib/actions.ts` but no page renders a control that calls them.
   The case detail page is read-only apart from messaging.
3. **There is no contractor portal.** The brief's core workflow — assign a
   contractor, they accept and upload before/after photos over a secure link —
   has no route. The cleaner equivalent (`/c/[token]`) exists and is the pattern
   to copy.
4. **There is no owner view.** No route, though `readByOwner`/`getInbox` exist.
5. **No filtering or search** on the case list or property list, although
   `listCases` and `listProperties` already accept filter objects.
6. **Notifications** exist only for completed cleaning jobs.
7. **QR** can be previewed but not downloaded, and the token cannot be rotated.
8. **Landing page** has hero, three steps and benefits only; no FAQ, no pilot
   form.
9. **No tests.**

## Decisions and assumptions

- **Keep the in-memory store.** Adding a real database is not possible without an
  external account, and the store already has the right shape. New entities are
  added to the same store with the same `organizationId` discipline. The
  `supabase/schema.sql` file is updated alongside so a future migration is
  mechanical.
- **`CaseStatus` is extended additively.** The brief lists nine issue statuses;
  the code has five. Adding the four missing values keeps existing seed data and
  logic valid. `resolved` is presented as "Completed".
- **Cleaning statuses stay as they are.** The six existing values already cover
  the brief's eight once `scheduled + cleanerId` is read as "assigned" and
  `completed` as "awaiting inspection". Churning this enum would risk a working
  flow for no user-visible gain; the mapping is documented instead.
- **Secure links over accounts** for contractors, cleaners and owners, matching
  the brief and the existing cleaner portal.
- **No new runtime dependencies.** The test runner is the only addition, as a
  dev dependency.

## Risks

- The in-memory store resets on every dev-server restart. Anything a reviewer
  types disappears on reload. This is called out in the README and the summary.
- Extending `CaseStatus` touches `labels.ts`, `status.ts` and any exhaustive
  switch. Caught by `tsc`, which is run after the change.
- Photo "uploads" are data URLs held in memory, not real object storage. Marked
  as demo-only.

## Expected result

A manager can take a guest report from arrival to approval: triage it, assign a
contractor, watch the contractor accept and document the work over a secure
link, approve it, and have the owner see the outcome — with cleaning running the
same loop, all of it translated, and the whole thing covered by tests.
